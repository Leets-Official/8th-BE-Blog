# API 오류 응답과 Swagger 선언 검증 보강

Status: complete

## Problem Statement

API 사용자는 잘못된 요청을 보냈을 때 원인에 맞는 응답 코드를 받아야 하며, Swagger 문서에서도 해당 API의 오류를 확인할 수 있어야 한다.

API별 오류 예시 분리는 완료했지만, 새 API에 `@ApiErrorCodes`를 빠뜨리는 것을 기존 14개 API의 고정 목록 테스트만으로 막기는 어렵다. 요청 본문 누락과 JSON 변환 실패는 원인 예외 유무로 구분하고 있어 분류 기준을 검증할 필요가 있다. 오류 응답의 `data`는 `null`이라는 계약이 있지만, 데이터를 받는 실패 생성 메서드도 남아 있어 계약을 위반하는 사용이 가능하다.

## Solution

신규 API의 오류 문서 선언 누락을 자동 검출하고, 요청 본문 오류를 실제 요청에 따라 검증하며, 실패 응답 생성 인터페이스를 공개 오류 계약에 맞춘다.

Swagger 선언 누락 검사를 우선 작업으로 진행한다. 본문 오류 분류와 실패 응답 생성 인터페이스 정리는 각각 별도 작업으로 검토·검증한다. 이미 완료한 API별 오류 예시 생성을 다시 구현하지 않는다.

## User Stories

1. As an API 사용자, I want 각 API에서 발생 가능한 오류를 Swagger에서 확인하고 싶다, so that 오류 코드별 처리를 구현할 수 있다.
2. As an API 사용자, I want 게시글 조회에서 신고·검색 오류 예시가 섞이지 않기를 원한다, so that 해당 작업의 오류 범위를 정확히 이해할 수 있다.
3. As an API 사용자, I want 본문이 없는 GET에 본문 누락 오류가 표시되지 않기를 원한다, so that 실제 요청 형태에 맞는 문서를 볼 수 있다.
4. As an API 개발자, I want 새 API의 오류 선언을 빠뜨리면 검증이 실패하기를 원한다, so that 문서 누락을 변경 반영 전에 발견할 수 있다.
5. As an API 개발자, I want 업무 오류가 없는 API도 명시적으로 선언하고 싶다, so that 의도적인 빈 목록과 선언 누락을 구분할 수 있다.
6. As an API 개발자, I want 프로젝트의 실제 등록 API를 기준으로 선언 여부를 확인하고 싶다, so that 신규 API를 고정 목록에 추가하지 않아도 누락을 발견할 수 있다.
7. As an API 개발자, I want Swagger·프레임워크 내부 엔드포인트가 프로젝트 API 검사에서 제외되기를 원한다, so that 관련 없는 코드 때문에 검증이 실패하지 않는다.
8. As an API 사용자, I want 필수 본문을 보내지 않았을 때 본문 누락 코드를 받고 싶다, so that 본문을 추가해 요청을 수정할 수 있다.
9. As an API 사용자, I want 잘못된 JSON을 보냈을 때 잘못된 입력 코드를 받고 싶다, so that JSON 형식을 수정할 수 있다.
10. As an API 사용자, I want JSON 필드 타입이 잘못됐을 때 본문 누락으로 안내되지 않기를 원한다, so that 수정할 원인을 정확히 알 수 있다.
11. As an API 사용자, I want DTO 검증 실패에서 구체적인 안내 메시지를 받고 싶다, so that 잘못된 필드를 수정할 수 있다.
12. As an API 사용자, I want 오류 응답의 데이터가 항상 null이기를 원한다, so that 성공 응답과 같은 데이터 처리 규칙을 적용하지 않아도 된다.
13. As an API 개발자, I want 실패 응답 생성 인터페이스가 오류 계약에 맞기를 원한다, so that 실수로 오류 데이터가 포함되는 사용을 줄일 수 있다.
14. As an API 개발자, I want 오류 코드와 HTTP 상태의 기존 매핑을 유지하고 싶다, so that 클라이언트의 분기 동작을 보존할 수 있다.
15. As an API 사용자, I want 문서의 기본 메시지와 실제 상황별 메시지가 구분되기를 원한다, so that 메시지 문구 대신 응답 코드로 안정적으로 분기할 수 있다.
16. As a reviewer, I want 세 개선을 독립적으로 검토할 수 있기를 원한다, so that 문서 검증과 런타임 응답 변경의 영향을 각각 평가할 수 있다.

## Implementation Decisions

- 기존 의미 중심 응답 코드와 HTTP 상태 매핑, 공통 응답의 `success`·`code`·`message`·`data` 계약을 유지한다. ADR-0002를 따른다.
- 기존 `@ApiErrorCodes`와 `OperationCustomizer` 기반 API별 예시 생성을 유지한다. 이번 작업의 우선순위는 신규 API의 선언 누락 검출이다.
- Spring에 등록된 프로젝트 REST API 메서드를 검사 대상으로 삼는다. 프레임워크·Swagger 내부 엔드포인트는 제외한다.
- 업무 오류가 없는 API도 빈 `@ApiErrorCodes`를 명시한다. 고정된 엔드포인트 개수만으로 선언의 완전성을 판단하지 않는다.
- 어노테이션 누락 시 어느 API 메서드가 누락됐는지 확인할 수 있게 한다.
- 본문 오류 분류는 우선 실제 HTTP 요청으로 현재 동작을 재현한다. 원인 예외 유무만으로 본문 누락을 판단하는 기준의 타당성을 확인하고, 본문 부재와 변환 실패를 구분하도록 필요한 변경만 수행한다. 구체적인 탐지 방식은 구현 시 조사 결과에 따라 정한다.
- 필수 본문 누락은 HTTP 400 `MISSING_REQUEST_BODY`, 잘못된 JSON과 본문 필드 타입 오류는 HTTP 400 `INVALID_INPUT_VALUE`를 기준으로 검증한다. DTO 제약 위반의 `INVALID_INPUT_VALUE`와 구체적인 메시지 처리는 유지한다.
- 실패 응답 생성 메서드의 사용처를 확인한다. 현재 확인된 예외 처리기는 데이터를 받지 않는 실패 생성 메서드를 사용하므로, 데이터 인자를 받는 미사용 오버로드의 제거를 우선 검토한다. 이미 사용처가 생겼다면 먼저 기존 `data: null` 계약에 맞게 이전한다.
- 공용 생성자 등을 포함한 응답 객체 전체 설계를 이번 작업에서 전면 개편하지 않는다. 지원하는 실패 생성 경로와 실제 오류 응답이 계약을 지키는지 검증한다.
- 세 작업은 독립된 로컬 이슈로 나눈다. Swagger 선언 누락 검사를 먼저 수행하고, 런타임 관련 두 작업은 별도 변경 단위로 다룬다.

## Testing Decisions

- 주 검증 경계는 기존 Spring Boot·MockMvc 통합 테스트다. 실제 요청에 대한 HTTP 상태와 JSON 응답, 생성된 OpenAPI JSON을 검증한다. 별도 외부 서버 테스트 기반은 추가하지 않는다.
- 런타임 오류 응답과 문서 생성 결과는 공개 동작으로 검증한다. 내부 헬퍼 호출 횟수나 특정 예외의 cause 구조를 정답으로 삼는 테스트는 피한다.
- 선언 누락은 등록된 API 메서드를 대상으로 하는 좁은 구조 검사로 보완한다. 이는 실행 결과만으로는 구분하기 어려운 선언 누락을 검사하는 목적이다.
- 기존 API별 OpenAPI 오류 예시 검증을 재사용한다. HTTP 상태와 예시 코드의 일치, 관련 없는 코드의 배제, 공통 500 예시를 유지한다.
- 입력 검증은 필수 본문 부재, JSON 구문 오류, 본문 필드 타입 오류, DTO 제약 위반을 요청으로 재현한다. 오류 응답에 `success: false`와 명시적인 `data: null`이 포함되는지 확인한다.
- 기존 공통 응답 객체 테스트는 실패 생성 인터페이스가 null 데이터를 만드는지 확인하는 데 재사용한다. 가능한 검증은 HTTP 응답 경계에 둔다.
- 선행 사례는 기존 Swagger 문서 통합 테스트, 입력 오류 컨트롤러 테스트, 공통 응답 객체 테스트다. 변경된 동작에 필요한 검증 후 전체 테스트를 수행한다.
- 사용자가 본 명세의 구현을 요청한 범위에서 기존 MockMvc, 등록 메서드 검사, 공통 응답 객체 테스트를 사용했다. 외부 서버 검증을 추가하지 않았다.

## Out of Scope

- 완료된 API별 Swagger 오류 예시 분리의 재구현
- 응답 코드 enum의 이름·HTTP 상태 변경, API 버전 변경
- 인증·인가 도입이나 신규 업무 오류 추가
- 업무별 예외 처리기 통합 및 서비스·도메인 리팩터링
- 모든 예외 분기와 Swagger 선언의 완전한 자동 추론
- 응답 객체 생성자·직렬화 구조의 전면 개편
- 외부 서버 테스트 기반 구축, PR 게시·원격 리뷰 답변

## Further Notes

- 선행 Swagger 개선은 `c2a759e`에 커밋돼 있다. 본 명세는 그 이후의 후속 개선이다.
- 본문 분류 문제가 실제 잘못된 응답으로 재현됐다고 단정하지 않는다. 현재 분류 기준의 취약 가능성을 검증하는 작업이다.
- 신규 용어나 기존 아키텍처 결정을 바꾸지 않으므로 용어집과 ADR을 추가하지 않는다.
- 로컬 이슈 순서는 01 선언 누락 검사, 02 본문 오류 분류 검증·보강, 03 실패 응답 생성 인터페이스 정리다.

## Implementation Results

- 등록된 프로젝트 API 메서드를 동적으로 검사하는 선언 누락 검증을 추가했다. 헬스체크 어노테이션의 일시 제거로 경로·메서드가 표시되는 실패를 확인한 뒤 복원했다.
- 본문 부재·JSON 구문 오류·본문 필드 타입 오류·DTO 제약 위반을 MockMvc로 검증했다. 현재 분류가 명세대로 동작하므로 예외 처리 로직은 유지하고 회귀 검증을 보강했다.
- 데이터 인자를 받는 실패 생성 메서드는 사용처가 없어 제거했다. 직렬화 결과와 실제 HTTP 오류 응답에서 `data` 필드의 존재와 null 값을 확인했다.
- `./gradlew test`: 109개 테스트 통과, 실패·오류·건너뜀 0건. `git diff --check` 통과.
- 작업 시작점 `2434a1b` 이후 변경을 Standards·Spec 두 축으로 독립 리뷰했다. 각 축의 발견 사항은 0건이었다.
