# 4주차 신고·댓글 조회 티켓 분할안

상태: 사용자 승인 후 01~06 티켓 발행 및 구현 완료. 모두 resolved.

이 문서는 대화에서 확정한 결정을 반영한다. 관리자 역할 없이 신규 API 5개를 구현하며, spec도 최종 합의에 맞춰 갱신했다.
공통 응답의 문자열 code 및 ResponseEntity 반환 통일은 이미 작업되어 있으므로 새 구현 티켓으로 중복 등록하지 않는다.

## 01. 게시글 목록의 공통 페이징 응답 적용

Blocked by: 없음.

게시글 목록·검색의 data를 items, page, size, totalElements, totalPages로 변경한다. page는 1부터, size는 기본 10·최대 100이며 생성 시각 내림차순, ID 내림차순으로 정렬한다. 새 댓글·신고 목록도 사용할 공통 페이징 규격을 제공한다. 정상 조회, 빈 결과, 검색 결과의 전체 건수, 페이지 경계 및 잘못된 파라미터를 HTTP 테스트로 검증하고 API 문서를 갱신한다.

## 02. 중복 방지를 포함한 게시글 신고 접수

Blocked by: 없음.

POST /posts/{postId}/reports에서 존재하는 사용자의 신고를 PENDING으로 생성하고 신고 당시 제목·본문을 저장한다. 본인·숨김 게시글 신고를 차단한다. 기존 게시글은 ACTIVE, 기존 신고는 PENDING으로 보정하며 기존 데이터를 보존한다. 기존 중복 신고를 자동 삭제하지 않고 점검할 절차를 제공한다. 신고자·대상 종류·대상 ID의 DB 유니크 제약과 동시 접수 테스트로 1건만 생성됨을 검증한다. 중복 신고는 409이며 처리 완료 후에도 재신고를 허용하지 않는다. 잘못된 사유와 사용자·대상 없음도 검증한다.

## 03. 댓글 목록·본문 검색 및 페이징

Blocked by: 01 — 공통 페이징 규격을 사용.

GET /posts/{postId}/comments에서 댓글·대댓글을 parentId를 가진 평평한 최신순 목록으로 반환한다. keyword가 있으면 해당 게시글의 댓글 본문을 검색한다. 목록에서 숨김·삭제 댓글은 원문 대신 안내 문구와 상태를 반환하고 검색에서는 제외한다. 숨김 게시글 조회는 404다. 필요한 공개 상태와 기존 데이터 보정도 이 티켓의 동작 범위에 포함하며, 02와 함께 진행할 경우 같은 상태 정의를 공유한다. 부모가 다른 페이지에 있어도 parentId를 유지한다. 필터를 DB 페이징 전에 적용하고 전체 건수를 검증한다.

## 04. 중복 방지를 포함한 댓글 신고 접수

Blocked by: 02 — 신고 접수 규칙과 유니크 제약, 03 — 댓글 공개 상태와 조회 정책.

POST /comments/{commentId}/reports에서 댓글 본문 스냅샷과 함께 신고를 생성한다. 본인·삭제 댓글, 숨김 댓글, 숨김 게시글의 댓글 신고를 제한한다. 03에서 도입한 댓글 공개 상태를 사용한다. 동일 사용자의 동일 댓글 중복 신고를 차단하고, 다른 사용자·다른 대상 종류의 신고는 허용한다. 상태 검사와 동시 신고를 HTTP·DB 테스트로 검증한다.

## 05. 신고 목록·스냅샷 검색 및 필터

Blocked by: 01 — 공통 페이징 규격, 02 — 신고 생성·상태·스냅샷 규칙.

GET /reports에서 전체 신고를 최신순으로 조회한다. status, targetType, targetId 필터를 AND로 적용하고 keyword는 신고 사유·제목 스냅샷·본문 스냅샷 중 하나라도 포함하면 일치시킨다. 현재 대상 원문은 검색하지 않는다. 대상이 삭제되어도 보존된 스냅샷을 조회할 수 있다. 신고 ID, 신고자, 대상, 상태, 사유, 스냅샷, 생성 시각을 제공한다. 관리자 검사는 추가하지 않는다. 빈 결과, 복합 조건, 전체 건수 및 잘못된 조건을 검증한다.

## 06. 신고 처리와 콘텐츠 숨김을 기존 조회에 연결

Blocked by: 04 — 두 종류 대상 신고와 댓글 공개 조회가 동작. 01·02·03은 간접 의존성.

PATCH /reports/{reportId}/resolve에서 존재하는 사용자라면 누구나 신고를 처리하고 처리자 ID를 기록한다. HIDE/KEEP 모두 PENDING을 RESOLVED로 전환한다. HIDE는 대상만 숨기고 KEEP는 현재 공개 상태를 유지한다. 다른 신고로 숨겨진 대상을 복원하지 않는다. 처리 결과·사유·처리 시각을 기록한다. 신고 당시 스냅샷으로 판단하며 HIDE는 수정된 현재 대상을 숨긴다. 삭제 대상은 KEEP 종결이 가능하고 HIDE는 409다. 이미 처리한 신고는 409이며 최초 결과를 보존한다.

신고 행 잠금과 하나의 트랜잭션으로 동시 처리 및 부분 성공을 방지한다. 기존 수정·삭제와 숨김의 경합도 검증한다. 게시글 목록·검색·상세, 댓글 목록·검색에서 숨김 정책을 실제 HTTP 응답으로 확인한다. 게시글 상태 필터는 DB 페이징 전에 적용하고 숨김 후 수정해도 숨김을 유지한다. 과거 검색 이력과 검색어 사전은 유지한다. 다른 신고로 이미 숨겨진 대상, 접수 후 수정·삭제된 대상, 실패 시 롤백, 동시 처리, 기존 CRUD·검색·신고 보존을 검증한다. 사용자·게시글·댓글 fixture와 Swagger 시연 흐름을 제공한다.

## 의존성

- 01 → 03
- 01, 02 → 05
- 02, 03 → 04
- 04 → 06
- 01과 02는 선행 티켓 없이 시작할 수 있다.
- 05는 신고 처리의 선행 조건이 아니다. 생성 응답의 신고 ID로 처리를 검증할 수 있다.
- 각 티켓에 필요한 데이터 보정, API 문서와 테스트를 포함한다. DB·서비스·테스트만의 별도 수평 티켓은 만들지 않는다.
